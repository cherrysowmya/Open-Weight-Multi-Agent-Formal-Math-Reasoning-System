# V4 — discussion and isolated proof contexts

> Historical methodology notice: automatic tactic portfolios and prefix-salvage
> trials have been removed. Related commands, settings and assisted scores below
> describe older versions, not the current solver. See [agent-only repair](agent-only-repair.md).

> Development-tool commands in this guide require files excluded from the current
> public checkout. See [tool availability and historical recovery](development-tools.md).

V4 adds a thinking-enabled discussion partner, a fresh formal proof context,
and bounded context compression. All requests use the already loaded Qwen3-8B
through `ModelBackend.chat`. There is no extra model instance or provider-specific
code in these roles. MLX remains the local inference implementation.

## Run your own example

From the project root, with Kimina running:

```bash
.venv/bin/local-lean-agent --config config/local.toml solve \
  examples/my_v4.lean --v4 on --max-rounds 4 \
  --output runs/my_v4.proved.lean
```

Replace that input path with your Lean file. The sample contains an incomplete
proof of `0 ≤ x^2 ∧ x^2 ≤ x` for `0 ≤ x ≤ 1`. Its seed is checked before inference.
V4 is adaptive: an early successful repair can bypass its extra roles entirely.
Use `--v4 off` for an ordinary V3 solve. The existing `--informal-policy` flag
controls V3 separately. Terminal output remains compact; complete attempts and
request records are saved under the configured result directory.

## Routing and proof boundaries

The default trigger is two rejected **model-generated** candidates. The input
seed does not count toward that threshold. If a formal round remains, the agent:

1. Builds a packet with the immutable Lean task, current goals/hypotheses,
   recent compiler diagnostics, retrieved declarations, approved informal
   guidance if available, and a short summary of rejected attempts.
2. Calls the discussion partner in a fresh thinking-enabled context. Its JSON
   response contains a diagnosis, alternative strategies, and intermediate facts.
3. Gives usable public advice and the compact packet to a fresh formal request.
   This request consumes one of the existing formal rounds and has thinking off.
4. Checks task preservation and verifies the complete returned Lean file with
   Kimina. If it fails and budget remains, normal compiler-guided repair resumes.

The initial fresh-worker implementation focuses on the unresolved goal inside
its original task wrapper. It returns a complete candidate for the original
theorem, including all remaining goals. It does not yet generate independent
auxiliary theorem files or automatically splice a subgoal proof into a partially
elaborated Lean term. This keeps the verification boundary concrete while
providing the fresh subproblem context required for V4.

A discussion response is advisory and has no correctness verdict. Malformed,
truncated, or failed discussion calls are logged and consume the discussion call
budget; formal repair continues without that advice. A proof of only one goal,
a changed statement, or `sorry` cannot become a successful theorem attempt.

## Context and memory policy

Each request has its own conversation ID, exactly a system and current user
message, and `history_messages = 0`. No generator/verifier hidden reasoning or
full model conversation is copied into discussion or fresh-worker requests.
Compiler diagnostics and local goals are shared deliberately as task evidence.

Failure summaries are deterministic extracts of recent compiler categories and
diagnostics, with source iteration IDs. They require no summarizer model call.
Full traces stay in JSON/JSONL outside the model context. When a normal repair
prompt becomes too large, the main agent receives the same compact packet form.

Fresh/discussion contexts are capped at 8,192 tokens; the main context remains
12,288. V4 admits requests using a conservative UTF-8 byte estimate plus a
template reserve, including reserved output tokens. This is stricter than the
older characters/3 estimate, but is still an estimate rather than exact server
tokenization. Actual usage returned by MLX is recorded too.

Optional evidence can be shortened, with `truncated_fields` recorded both in
the request and audit data. The theorem and full selected goal/hypothesis text
are never truncated. If those cannot fit, the role fails or is skipped with a
context-budget diagnostic. Automatic semantic decomposition of an oversized
theorem is a later improvement.

The supplied configuration reuses one Qwen model sequentially. Discussion and
fresh worker have independent call limits, initially one each per theorem.
No discussion happens after the last available formal round.

```toml
[v4]
enabled = true
discussion_enabled = true
fresh_context_enabled = true
compression_enabled = true
trigger_after_failures = 2
max_discussion_calls = 1
max_fresh_calls = 1
max_context_tokens = 8192
discussion_max_output_tokens = 1536
fresh_max_output_tokens = 512
summary_max_chars = 2400
```

## Tests and paired evaluation

```bash
.venv/bin/python -m unittest tests.test_v4 tests.test_v4_evaluation -v

LOCAL_LEAN_AGENT_LIVE_LEAN=1 .venv/bin/python -m unittest \
  tests.test_v4_lean_integration -v

# Three cases under both V3 and V4 (six theorem attempts).
.venv/bin/python scripts/test-v4-live.py \
  --output runs/v4-ablation-latest.json

# One condition, or isolate either additional role:
.venv/bin/python scripts/test-v4-live.py --condition v4 \
  --output runs/v4-only.json
.venv/bin/python scripts/test-v4-live.py --condition discussion-only \
  --output runs/v4-discussion-only.json
.venv/bin/python scripts/test-v4-live.py --condition fresh-only \
  --output runs/v4-fresh-only.json
```

The live runner accepts `--case`, `--manifest`, and `--repetitions`. The initial
manifest includes hypothesis reasoning, a seeded nonlinear repair with multiple
goals, and a false theorem. References are used only for preflight checks and
are never passed to Qwen. Every claimed success is independently recompiled.
All conditions share V3 informal reasoning, retrieval, main generation settings,
and formal budgets. Whole-proof fallback tactics and prefix probes are disabled
for these comparisons. Condition order alternates by case/repetition. Extra
discussion token/time costs are measured, not equalized.

Existing V1/V2/V3 benchmark runners explicitly disable V4. Their historical
artifacts remain preserved. The V4 runner records effective configurations,
code/prompt fingerprints, checkpoints, and a final immutable artifact.

`v4_requests` records role, messages, conversation ID, compression fields,
source iterations, output budget, thinking mode, status and generation/error.
Metrics distinguish `main_agent_calls`, `fresh_subproblem_calls`, and
`discussion_partner_calls`. The legacy `model_calls`/`rounds` counter includes
completed main plus fresh formal calls, preserving the formal-round budget.
Discussion calls and tokens are additional. `v4_role_errors` and `v4_activated`
prevent an all-bypassed or broken-role run from being mistaken for role coverage.
`formal_call_attempts` also counts failed HTTP calls, while legacy `model_calls`
counts completed formal responses. The role-specific main/fresh counters count
attempted calls; the evaluation's `all_model_calls` includes these failed calls.
Summary `positive_successes` requires the independent recheck to pass;
`claimed_positive_successes` records pre-audit success claims separately.

## Scope of the evidence

The minimum implementation is the bounded routing and context behavior above.
Useful engineering improvements include exact backend token counting, richer
typed goal extraction, and separate auxiliary-lemma compilation with safe
reintegration. Research claims need repeated held-out V3/V4 pairs, separate
discussion and context ablations, and equal-compute comparisons. Success on a
small development fixture set does not establish that V4 improves accuracy.

Actual validation results are recorded in [V4 results](v4-results.md).
