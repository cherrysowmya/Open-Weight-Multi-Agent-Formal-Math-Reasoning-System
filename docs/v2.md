# V2 — local semantic retrieval

> Development-tool commands in this guide require files excluded from the current
> public checkout. See [tool availability and historical recovery](development-tools.md).

## Implementation boundary

`SemanticRetriever` is independent of `ModelBackend`. The concrete
`LeanExploreMCPClient` starts `lean-explore mcp serve --backend local`, performs
`search_summary`, and obtains `get_source_code` for the top results. It never
uses LeanExplore's hosted API, informalization pipeline, or agent tooling.
Qwen generation remains on MLX-LM; replacing that with vLLM later does not change
the retrieval adapter or proof loop. Lean/Kimina remains the only proof authority.

The first query is made before Qwen is loaded. Queries contain the original
theorem statement and, when available, the latest LSP goal. They exclude the
failed proof body so an invented identifier is not recycled into the query.
Identical queries are cached within an attempt. A fresh prompt receives a bounded
ranked packet with exact declaration names, IDs, descriptions, and source.

The process and index persist through a paired experiment. No formal specialist
is loaded. LeanExplore's 0.6B embedding model is not a second Qwen3-8B generation
instance. The default disables the extra cross-encoder reranker to limit memory.

## Setup and settings

Run `./scripts/setup-lean-explore.sh` from the project root. It uses Python 3.13
and installs `lean-explore[local]==1.3.0` in `services/lean-explore/.venv`.
The pinned index is `20260714_172516`; setup also downloads
`Qwen/Qwen3-Embedding-0.6B`. Data and Hugging Face caches stay under that service
directory. Runtime sets `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, and disables
OpenAI Agents tracing. The upstream package has optional API-related dependencies;
installing them does not mean the application calls them.

Important `[lean_explore]` settings in `config/local.toml`:

| Setting | Default | Meaning |
| --- | --- | --- |
| `enabled`, `required` | `true`, `true` | Fail visibly when configured retrieval is unavailable |
| `limit` | 8 | Ranked result names/descriptions returned per search |
| `source_limit` | 5 | Results for which Lean source is fetched |
| `rerank_top` | 0 | Disable cross-encoder only; hybrid lexical/semantic search remains |
| `packages` | `["Mathlib", "Init"]` | Mathlib plus the Lean core declarations it uses |
| `max_query_chars` | 4000 | Query bound |
| `max_context_chars` | 12000 | Retrieval packet bound within the overall 12K-token guard |
| `request_timeout_seconds` | 600 | Per MCP request deadline, including cold startup |

`doctor` performs real local search and prints the data version. If the model is
missing, run setup with internet access once; runtime deliberately will not fetch
weights. For a retrieval-free `solve`, set `enabled = false`. The benchmark
explicitly sets OFF/ON itself; V1's acceptance suite always sets retrieval OFF.

There is no reranker in this baseline. To experiment with `rerank_top > 0`, first
cache the corresponding Qwen reranker and re-profile memory. Do not assume the
current memory measurements cover that configuration.

## Fixture validation

`v2-validate` checks every repair seed and every positive reference proof with
the configured Kimina/Mathlib environment. It writes full diagnostics and source
hashes to `runs/v2-validation-latest.json`. The ablation repeats this preflight
automatically and refuses to run if fixtures are invalid. A verifier outage or
timeout does not count as a rejected seed.

Two initially proposed repairs were not repairs: `List.reverse_involutive xs`
compiled, and `Function.id_comp f` was definitionally compatible with the goal.
They were replaced before the reported run with `List.reverse_twice_identity`
and `Function.compose_identity_right`, whose rejection was confirmed by Lean.
The reference proofs for `List.length_reverse` and `List.length_append` use
implicit list arguments, as required by the installed library.

The 20 fixtures are 10 generation tasks, 8 seeded repairs, and 2 negative tests.
The negatives have explicit counterexamples: `n = 0` refutes `n + 1 = n`;
`α = ℕ`, `s = {0}`, and `t = ∅` refute universal union/intersection equality.
These concrete counterexamples also compile in `benchmarks/v2/counterexamples.lean`.
Expected names and reference proofs stay in the manifest, outside model prompts.

## Paired experiment

```bash
local-lean-agent --config config/local.toml v2-ablation \
  --repetitions 1 --output runs/v2-ablation-latest.json
```

Every case runs in both conditions, alternating which condition is first by
case and repetition. Both use the same Qwen3-8B 4-bit model, thinking disabled,
temperature 0, 512 output tokens, fresh bounded prompts, required Lean LSP, and
Kimina. Positive tasks get four model rounds; negative tasks get three.
The fallback portfolio is OFF in both conditions so general tactics do not mask
retrieval's contribution. Existing valid candidates are still verified first.
The control uses the same V2 prompt template with an empty retrieval section;
it is not a replay of the historical V1 prompt. All other wording is held fixed.

The experiment keeps one MLX process and one LeanExplore process for efficiency.
The retrieval process may remain resident during OFF cases, though those cases
do not call it or receive results. Timing therefore is a shared-process,
counterbalanced experiment, not an isolated cold-start service comparison.

Each attempt is saved under `runs/results/` and event telemetry in
`runs/attempts.jsonl`. The requested output is checkpointed after each attempt;
`experiment_complete: false` plus `status: running` is not a final score.
Final complete traces are also saved under `runs/history/`. The metadata and
code fingerprint are captured before generation starts. Effective settings,
case budgets, validated source hashes, and the full preflight are retained.

Independently recheck the final accepted proofs after the run:

```bash
.venv/bin/python scripts/audit-v2.py runs/v2-ablation-latest.json
```

This makes no model calls. It recompiles accepted proofs, checks task preservation,
checks every negative task's budget contract, and compiles the counterexamples.
It also rechecks rejected positive-task final candidates when they preserve the
original task, looking for orchestration false negatives.
Its full output is saved in `runs/v2-audit-latest.json`.

## Metrics and interpretation

- **Positive successes:** Lean-verified proofs out of the 18 true tasks.
- **Correct outcomes:** positives verified (repairs require a rejected seed),
  plus negative tasks exhausting their exact budget without a false positive.
- **Proof failures:** rejected model-generated candidate rounds. Input seeds
  are excluded. Duplicate rejected candidates count as unsuccessful model rounds
  but do not incur another Kimina check. Also report positive-only failures so
  mandatory rejection of false theorems is not confused with solver weakness.
- **Unknown-identifier failures:** generated rounds with Lean's unknown-identifier
  category or an explicit `unknown identifier`/`unknown constant` diagnostic.
  This is a proxy for name hallucination, not a semantic claim that every unknown
  name is fabricated. It excludes deliberately broken input seeds. One round
  with several such messages counts once. Generic field/type errors alone do not.
- **Expected-declaration recall:** fraction of positive cases where any annotated
  reference name appeared in the union of retrieved top-8 lists across rounds.
  This is an any-round hit rate, not per-query recall@8 and not proof of usage.
- **Reductions:** baseline count minus retrieval count; negative means regression.
  Success deltas use the opposite sign (retrieval minus baseline).
- **Cost:** model calls, tokens, context sizes, checks, retrieval latency, and
  process RSS samples. RSS samples are not peak total unified-memory accounting
  and omit some Lean/OS/Metal allocations. In particular, the current retrieval
  PID is the LeanExplore CLI launcher; its child search process is not included
  in that per-attempt RSS field. Do not treat it as total retrieval memory.

`experiment_complete` checks infrastructure completion and false-positive safety;
it does not assert a perfect score, causal improvement, or statistical significance.

## Research scope

The minimum viable result is a reproducible local paired run, including null or
negative results. These easy, related fixtures and descriptive theorem names
make this an integration/diagnostic suite, not an unbiased held-out benchmark.
An initial Mathlib-only diagnostic run was interrupted after an index coverage
audit showed that 12 of the 18 reference lemmas belong to `Init`. That partial
trace is preserved separately and is not included in the complete-run score.
The complete run uses both packages for every retrieval-enabled case.
All 13 distinct annotated names exist in the pinned database: eight in `Init`
and five in `Mathlib`. Across the 18 positive fixtures, those cover 12 and six
cases respectively. This was checked directly in the index, independently of
model outcomes or semantic-search rank.
The index can still differ from the installed library; compilation is the final
compatibility check.

Good engineering follow-ups are explicit package-coverage checks, exact symbol lookup,
query design, stronger process-memory profiling, and fully locked transitive
dependencies/model revisions. They should be compared in separate named runs,
not silently tuned midway through this run.

Potentially publishable work would require a larger deduplicated held-out corpus,
obfuscated task names, matched budgets, repeated paired runs, uncertainty estimates,
and failure annotation distinguishing retrieval misses from bad lemma application.
This single small run cannot support broad claims about retrieval or small models.

Upstream behavior is documented in the installed LeanExplore implementation and
the [official local backend documentation](https://github.com/justincasher/lean-explore/blob/main/docs/local-backend.md).
